# SCE Integration Fixture Layout (Non-W3C-IRP)

This document records the per-backend layout for hand-curated integration
fixtures — SCXML programs that exercise semantics not covered by the W3C
IRP suite. The W3C IRP suite (under `resources/<N>/test<N>.txml`, where
each fixture is regenerated to `test<N>.scxml` and consumed by the
per-backend W3C harnesses) remains the spec-conformance baseline; the
integration layer described here is strictly additive.

Only one such fixture exists today: `donedata_local_invoke`.

## Why this layer exists

W3C SCXML §5.5 (`<donedata>`) and §6.3.1 (`done.invoke.<id>` event
emission) interact when an inline child machine reaches a top-level
`<final>` carrying `<donedata>` and the parent reads
`_event.data` on the `done.invoke.<id>` event. No public W3C IRP fixture
exercises this combination directly — the IRP `<donedata>` tests cover
machine-level done emission, not the child-invoke-to-parent round trip.

The mesh suite covers the same contract for the AOT wire-18 path via
`test_mesh_session_f_donedata`. The integration layer documented here
covers the parallel *local-invoke* path.

## Per-backend coverage matrix

| Backend | Coverage form | Location | Drift-verify CI gate |
| --- | --- | --- | --- |
| Rust | AOT-generated tree | `sce-rust-tests/src/integration/donedata_local_invoke/` | yes |
| Kotlin | AOT-generated tree | `sce-kotlin-tests/src/main/kotlin/com/sce/generated/donedata_local_invoke/` | yes |
| Go | AOT-generated tree | `sce-go-tests/donedata_local_invoke/` | yes |
| C++ | Interpreter-only gtest | `tests/integration/DonedataLocalInvokeTest.cpp` | n/a (no committed generated tree) |
| Python | uncovered | — | — |
| C11 | uncovered | — | — |

The three AOT-generated trees are regenerated by per-backend scripts
(`scripts/regen_donedata_local_invoke.sh`, `…_go.sh`, `…_kotlin.sh`) and
guarded by `.github/workflows/drift-verify.yml` plus the
`scripts/hooks/pre-commit` drift-verify trigger.

## Why the asymmetry exists

The split is not a parity bug; it reflects two distinct engine
architectures and a known coverage gap:

1. **C++ has an Interpreter as a first-class engine.** The
   `DonedataLocalInvokeTest.cpp` gtest exercises the same SCXML contract
   directly against `runtime/StateMachine.h` (the Interpreter) and
   `SCXMLInvokeHandler`'s completion callback. C++ therefore does not
   need a committed AOT-generated tree to cover this contract — the
   Interpreter path is the canonical local-invoke code path on the C++
   side.
2. **Rust / Kotlin / Go are AOT-only backends.** They have no
   Interpreter; the only way to cover the contract is to compile a
   hand-authored fixture through `sce-codegen`, commit the generated
   tree, and run it under each backend's test harness. The
   `donedata_local_invoke` directory in each of those three repos is
   exactly that.
3. **Python and C11 are also AOT-only, but the fixture has not been
   ported.** This is currently an honest coverage gap, not a parity
   guarantee. Until a defect surfaces that this gap was hiding, the
   asymmetry is intentional rather than urgent: porting requires
   authoring per-backend regen scripts, drift-verify gates,
   pre-commit hook entries, and per-backend test harness wiring,
   none of which exist on those two backends today.

## Rust-side anchor

`sce-rust-tests/src/integration/mod.rs` is the only hand-authored file
in the Rust integration tree. Every other file under
`sce-rust-tests/src/integration/<stem>/` carries the standard §6.2.6
`SCE-GENERATED` drift header and `SCE-MAP:` markers, regenerated by the
per-fixture script. Adding or dropping an integration fixture on Rust
is a single-line edit to `mod.rs`; the W3C regen pipeline
(`sce-codegen generate-w3c -l rust`) deliberately does not touch this
tree.

The Kotlin and Go equivalents follow the same convention adapted to
their respective build systems.

## Adding a new custom integration fixture

When a future SCXML contract requires this layer:

1. Author the source `.scxml` under
   `sce-rust-tests/fixtures/<stem>.scxml` (and parallel locations for
   the other AOT-generated backends if porting).
2. Author a dedicated regen script `scripts/regen_<stem>.sh` (plus
   per-backend variants) that wraps the
   `sce-codegen generate ... --as-child` workflow following the
   pattern in `scripts/regen_donedata_local_invoke.sh`.
3. Register the new sub-module in
   `sce-rust-tests/src/integration/mod.rs` and the equivalent Kotlin
   and Go integration entry points.
4. Wire the §6.2.6 drift-verify CI gate to the new generated directory
   in `.github/workflows/drift-verify.yml` and the
   `scripts/hooks/pre-commit` drift-verify trigger.
5. If a backend that is currently in the *uncovered* row gains a
   custom integration fixture, update the matrix in this document
   with the new coverage form and gate status.

## Re-evaluation trigger

If a defect surfaces on Python or C11 that the
`donedata_local_invoke` contract would have caught, the per-backend
asymmetry above should be reopened and the fixture ported, not
backfilled silently.
